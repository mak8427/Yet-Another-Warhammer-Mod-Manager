# Development setup

## Scaffolding, fixtures, and benches

All developer tooling lives under `scripts/`, grouped by purpose:

| Directory | Purpose |
|---|---|
| `scripts/dev/` | developer setup helpers (`fetch-reference.sh`) and their tests |
| `scripts/qa/` | committed fixtures, the parity and performance gates, screenshot capture, and their tests |
| `scripts/perf/` | benchmark workload generators, the Criterion runner, and the measurement harnesses |

The root `package.json` scripts are the single documented entry point. Run them
from the repository root after `pnpm install --frozen-lockfile` (the parity
report reads the root `yaml` dependency):

```bash
pnpm reference          # fetch the pinned legacy checkout (network, idempotent)
pnpm test:reference     # test the fetch script in throwaway repositories
pnpm fixtures:verify    # verify committed fixtures; regenerate and verify the perf workloads
pnpm fixtures:write     # regenerate the committed QA fixtures (review the diff before committing)
pnpm fixtures:perf      # regenerate only the 100/500/2000-pack perf workloads
pnpm bench              # generate + verify workloads, then run the Criterion bench
pnpm bench:budget       # enforce the scan budgets (perf-budget host; see docs/PERF.md)
pnpm qa:scripts         # run the Node tests for the fixture, parity, and perf-gate scripts
pnpm perf:gate          # release performance gate; strictness is unchanged
pnpm parity:check       # capability-parity gate; strictness is unchanged
```

`perf-fixture/` is generated on demand and gitignored; the generator is
deterministic, so a clean checkout reproduces the same bytes. The committed QA
fixtures under `fixtures/` are never rewritten unless you run
`pnpm fixtures:write`. CI runs the same commands and paths
(`.github/workflows/ci.yml`).

Benchmarks and their measured evidence stay in place: the Criterion suite is
`crates/wh3mm-core/benches/hot_paths.rs`, the workloads are generated by
`scripts/perf/generate-suite.mjs`, and the release gates are
`scripts/qa/verify-perf-gate.mjs` and `scripts/qa/parity-report.mjs`.

## Legacy WH3 Mod Manager reference

The legacy application ([`Shazbot/WH3-Mod-Manager`](https://github.com/Shazbot/WH3-Mod-Manager))
is the reference for M1/M2 porting work (UI, pack handling, load order) and for
the WAR-7 performance baselines. It is **not** part of this repository and is
never vendored, committed, or shipped.

### Pinned revision

| Field | Value |
|---|---|
| Repository | `https://github.com/Shazbot/WH3-Mod-Manager.git` |
| Commit | `07fcf3ea1428fe3aa88282ba7aed44d9947ef103` |
| Commit date | 2026-10-19 |
| License | MIT (upstream `LICENSE`) |

### Fetch it

From the repository root:

```bash
pnpm reference   # or: bash scripts/dev/fetch-reference.sh
```

The script creates a shallow, detached checkout at `reference/WH3-Mod-Manager`
with exactly the pinned commit. It requires `git` and network access to GitHub.
The command is idempotent: when the checkout already exists at the pinned
commit it prints a confirmation and exits without changing anything.

`reference/` is listed in `.gitignore`, so the checkout never appears in
`git status` and never reaches a commit. No CI job needs to fetch it; any job
that does can call the same script.

### Read-only rule

Treat `reference/WH3-Mod-Manager` as read-only. Do not edit files there, do not
commit them, and do not copy the tree into the product. Use it to read the
legacy implementation, then write the Rust or TypeScript version in this
repository. Local edits make the checkout disagree with the pinned commit and
invalidate comparisons against the legacy baselines.

### Verify

```bash
git -C reference/WH3-Mod-Manager rev-parse HEAD   # prints the pinned commit
git status --porcelain                            # clean
git check-ignore reference/WH3-Mod-Manager        # prints the path
git ls-files reference/                           # prints nothing
```

### Re-pin

1. Pick the new upstream commit and update `PINNED_COMMIT` in
   `scripts/dev/fetch-reference.sh` and the table above (commit and date).
2. Remove the old checkout: `rm -rf reference/WH3-Mod-Manager`.
3. Run `pnpm reference` and repeat the verification commands.
4. Record why the revision moved in the task or pull request that changes it.
